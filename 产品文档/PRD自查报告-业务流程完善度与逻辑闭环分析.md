# 党建管理系统 PRD 自查报告：业务流程完善度、功能缺失与逻辑闭环分析

> **评估对象**：`党建管理系统完整产品架构方案（PRD版）.md`、`党建管理系统页面结构交互说明与视觉规范.md`、`党建管理系统设计落地计划.md`
> **评估目的**：自查整体业务流程是否完善、功能是否有缺失、逻辑是否闭环
> **评估口径**：以《中国共产党发展党员工作细则》《中国共产党支部工作条例》等刚性党务规则为合规底线，以"强流程、重留痕、分级管控、基层减负"为产品原则，逐项核验

---

## 一、评估结论（总览）

**总体判断：架构分层与五大核心场景覆盖度较高，但作为"可落地的刚性党务系统"仍存在多处阻断级与中等级缺口，逻辑闭环在 7 条主流程中约有 3 条存在开口，需在一期/二期前补齐。**

| 维度 | 评级 | 说明 |
|---|---|---|
| 整体业务架构 | 良 | 六层架构、五大场景（党务/党员/组织生活/学习教育/监督考核）覆盖完整，安全合规前置到位 |
| 业务流程完善度 | 中 | 三会一课、党费、换届闭环清晰；发展党员、组织关系转接、积分考核存在合规与状态缺口 |
| 功能缺失 | 中（含阻断项） | 角色矩阵缺党总支级、发展党员缺法定公示、举报/处分无闭环、核心流程数据表未建模 |
| 逻辑闭环 | 中 | 7 条主流程中"组织撤销、发展党员、三会一课、党费、整改"基本闭环；"组织转接、积分考核、信访举报"存在开口 |
| 文档一致性 | 中 | 发展党员阶段在 3.2.2 与 4.1 划分不一致；终端接入范围在设计规范中被收窄 |

---

## 二、整体业务流程完善度（分模块评估）

### 已较为完善的模块
- **组织架构管理（3.1）**：组织树全生命周期、撤销/合并/划转校验、换届提醒与线上选举，规则清晰，闭环完整。
- **三会一课（3.3.1）**：计划→通知→签到→纪要→补学→台账归档，含频次校验与台账必填要素拦截，闭环严谨。
- **党费管理（3.5）**：核算→收缴→催缴→使用审批→公示→上缴→对账，链路完整，减免与红色预警到位。
- **换届选举（3.1.2）**：到期提醒、流程节点、线上无记名投票计票，合规性好。
- **安全与数据权限模型（2.2.6 / 5.2）**：自上而下穿透、平级隔离、字段脱敏、审计留痕，逻辑自洽。

### 存在缺口的模块（详见第四节）
- 发展党员流程（合规硬伤 + 节点未枚举 + 阶段划分不一致）
- 组织关系转接（转接中状态缺失、外部系统失败处理缺失）
- 监督考核（积分自动联动规则、申诉闭环、评议结果应用不清）
- 党风廉政（信访举报无处理闭环、党纪处分无工作流）
- 特色业务（移动端入口与设计范围冲突）

## 三、逻辑闭环评估表（主要流程）

| 主流程 | 闭环状态 | 开口 / 风险点 |
|---|---|---|
| 组织撤销 / 合并 / 划转 | ✅ 闭环 | 撤销前强制党员划转 + 未结流程拦截，逻辑严密 |
| 发展党员全流程 | ⚠️ 部分闭环 | 节点校验拦截有效，但**缺失法定"公示"环节**；25 节点未枚举；3.2.2 与 4.1 阶段划分不一致 |
| 组织关系转接 | ⚠️ 开口 | 转接中党员**无中间状态**，易发生"双重归属/统计漏计"；外部系统回执未回传/超时无处理路径 |
| 三会一课 | ✅ 闭环 | 计划→执行→补学→归档，台账要素拦截完整 |
| 党费管理 | ✅ 闭环 | 催缴→预警→组织处理链路完整；但**跨年基数核定与转接月份归属**未定义 |
| 积分 / 考核 | ⚠️ 开口 | 积分"每日自动核算"但**来源联动规则未定义**；申诉状态机缺失；评议结果如何转为积分等次不清 |
| 信访举报 | ❌ 未闭环 | 仅声明"匿名/实名举报（加密）"，**无接收、分办、核查、反馈、归档的处理流程** |
| 整改跟踪 | ✅ 基本闭环 | 组织生活会/支部考核均有销号，但**多来源整改是否统一台账未明确** |

## 四、功能缺失清单（按严重级别）

### 【高 / 阻断级】—— 须在一期前补齐，否则影响权限落地或合规性

**H1. 角色矩阵缺失"党总支管理员"与"党小组长"**
- 位置：5.1 四级标准角色矩阵仅含 `超级管理员 / 党委管理员 / 支部管理员 / 普通党员`，但组织架构为 `党委 → 党总支 → 党支部 → 党小组` 四级（2.2.1 / 3.1.1.1）。
- 问题：党总支层级的管理操作（审核下级支部、计划审批）在矩阵中无明确载体；党小组会（每月1–2次）需党小组长记录但无对应角色。数据权限"自上而下穿透"在 4 级组织与 4 角色间无法精确映射。
- 建议：补充 `党总支管理员` 角色行，明确其与党委/支部的权限差；视需要增设 `党小组长`。

**H2. 发展党员流程缺失法定"公示"环节（合规硬伤）**
- 位置：3.2.2 / 4.1 全流程节点。
- 问题：依据《发展党员工作细则》，须在"确定入党积极分子、确定发展对象、接收预备党员前、预备党员转正前"进行公示。PRD 五阶段均未显式包含公示节点，却声称"严格遵循 25 个节点"。
- 建议：在对应阶段插入公示节点（公示期、公示范围、异议受理、公示结果归档），作为进入下一环节的校验条件。

**H3. 转接中党员状态缺失，统计口径存在双重归属风险**
- 位置：3.2.3 组织关系转接 + 6.2 党员档案主表 `party_status` 枚举（正常/预备/停止党籍/出党/死亡）。
- 问题：转接在途（转出已审、转入未接收）期间，党员既不应计入转出方也不应计入转入方完整统计，但数据模型无"转接中"状态；会导致统计重复或漏计、驾驶舱数据失真。
- 建议：在 `party_status` 或 `identity_type` 增设"转接在途"中间态，并明确在途期间党费归属与组织生活归属规则。

**H4. 发展党员 25 节点未枚举，且 3.2.2 与 4.1 阶段划分不一致**
- 位置：3.2.2（5 阶段：申请入党/培养考察/发展对象/接收预备/转正归档）vs 4.1（将"发展对象"并入"接收预备党员阶段"，并以"上级党委备案审查"开篇）。
- 问题：两处阶段边界不同；4.1 将"上级党委备案"（发展对象阶段）与"上级党委审查/预审"（接收前）合并为"上级党委备案审查"，弱化了《细则》中"备案"与"预审"两个独立党委动作。
- 建议：以《细则》为准统一为单一权威节点清单（建议直接给出 25 节点表），3.2.2 与 4.1 引用同一清单，避免实现歧义。

**H5. 核心流程/积分/学时/考核数据表未纳入数据模型（留痕可溯存疑）**
- 位置：第六章仅给出 `org_info / party_member_info / org_life_record / party_fee_detail` 四张表。
- 问题：发展党员流程实例、组织关系转接实例、审批/工作流实例、学习学时记录、积分明细、考核与整改记录、消息/待办、审计日志等支撑"全程留痕、不可逆向删除"的关键实体均未建模。仅有主数据表无法保证流程可追溯。
- 建议：补充流程实例表、积分/学时表、考核/整改表、消息待办表、审计日志表，并在权限与脱敏层面一并定义。

**H6. 信访举报无处理闭环**
- 位置：3.7.2 党风廉政仅声明"匿名/实名信访举报（全程加密保密）"。
- 问题：举报提交后由谁接收、如何分办、核查、反馈、归档、保密留痕均无流程；页面规范也未设计举报入口（4.7 移动端无举报项）。形成"有入口无闭环"的空头功能。
- 建议：定义举报受理工作流（接收→分办→核查→处置→反馈→归档），明确受理角色与保密审计，并在移动端补充举报入口。

**H7. "请假"业务无工作流模板，但业务强依赖审批**
- 位置：3.3.1.2 请假机制（党员申请、书记审批）；2.2.3 工作流引擎预置模板仅列"发展党员、组织关系转接、党费使用、换届审批、信息变更"，**不含请假**。
- 问题：请假需审批才能"不计入缺席"，却无对应流程引擎模板与待办生成规则，三会一课缺席判定逻辑无法闭环。
- 建议：将"请假审批"纳入工作流预置模板，并明确其与签到/缺席/补学的状态联动。

### 【中 / 应修复】—— 二期前补齐，影响自动化与体验

**M1. 积分/学时/党费/民主评议的自动联动规则未定义**
- 积分"每日凌晨自动核算"（3.7.1），但未说明：党费欠缴何时转化为扣分、学时未达标如何计入基础分缺失项、志愿服务/双报到时长如何同时兑换学时与积分（是否去重）、民主评议等次如何由积分推导。
- 建议：给出一份"积分与学时自动核算规则映射表"，明确各扣分项触发时机与数据源。

**M2. 账号开通与党员绑定/初始配流程缺失**
- 普通党员如何获得登录账号（手机号绑定？身份证+姓名？邀请码？）、初始密码与激活流程、与政务统一身份认证/企业微信的账号映射均未定义。一期无此流程则"党员端"无法启用。
- 建议：补充账号生命周期（开户/激活/找回/注销）与身份绑定规则。

**M3. 党费基数在"无财务对接"的 early-phase 录入来源未定义**
- 3.5.1 工资基数对应比例可配置、每年1月核定；财务/人事系统对接排在第三期。一期无对接时，基数由谁录入、如何校验、党员是否可见计算明细未说明。
- 建议：定义一期人工核定流程与字段来源，并考虑向党员展示"基数×比例"计算明细以满足透明性。

**M4. 外部系统（全国党员管理信息系统）对接的失败/超时/回执未回传处理缺失**
- 3.2.3.2 跨省转接依赖全国系统回执回传。若外部系统宕机、驳回或回执长期未回传，本地转接实例将挂起，无超时/异常处理与人工介入路径。
- 建议：定义对接异常状态（待回执/回执超时/对接失败）与人工兜底流程。

**M5. 党纪处分无工作流，且与积分/考核联动缺失**
- 3.7.2 提及"违纪处分记录"，党籍异动（3.2.4）含开除党籍/除名等，但警告/严重警告/撤销党内职务/留党察看等"处分"无独立审批流程，亦未说明处分如何影响积分扣分、考核等次、评优资格。
- 建议：补充党纪处分工作流与对积分/考核的联动规则。

**M6. 审计日志访问角色缺失（安全合规）**
- 2.2.6 / 9.1 要求操作全程留痕、日志不可篡改，但 5.1 角色矩阵无"审计/合规管理员"，未定义谁可查询与导出审计日志。
- 建议：增设审计查看角色或明确超级管理员专属，并定义日志查询的最小权限原则。

**M7. 电子签章业务触发场景未明确绑定**
- 2.2.3 电子签章列为能力（电子介绍信/审批单据/证明材料），但 3.2.3.2 跨省转接生成电子介绍信时未显式要求签章；党员证明开具亦无专门功能。能力有但业务触发点模糊。
- 建议：在跨省转接介绍信、各类证明开具、关键审批单据处显式声明签章节点。

**M8. 周期重置 / 跨年 rollover 逻辑缺失**
- 党费基数年度核定、学时年度/季度要求、积分核算、年度考核均涉周期边界，但"跨年如何清零/结转/历史归档、统计口径如何切换"未定义，易致跨年数据错乱。
- 建议：定义各周期指标的结转/重置规则与历史快照策略。

**M9. 换届委员届中调整（补选/免职）流程缺失**
- 3.1.1.2 仅通过换届更新委员分工；届中委员出缺（离职/免职/补选）无流程，组织档案委员信息无法及时更新。
- 建议：补充届中委员调整审批流，并联动组织档案。

**M10. 移动端入口与 PRD 终端层声明不一致（范围缺口）**
- PRD 终端层（2.2.5）声明小程序含"志愿服务打卡、请假申请、心得提交"；但设计规范 4.7 移动端仅含"首页/待办/签到/学习/党费/我的"，落地计划 Task 4 移动端 P0 亦未含志愿服务/双报到/活动报名/举报。
- 建议：明确移动端二期功能清单，将志愿服务打卡、活动报名、请假、举报纳入移动端规划，消除与终端层声明的冲突。

**M11. 终端接入范围在设计规范中被收窄（范围缺口）**
- PRD 终端层含 PC / 微信小程序 / 政务钉钉·企业微信内嵌端 / 数据指挥大屏 / H5 五类；设计规范设计范围仅"PC 管理端、党员移动端、党委数据驾驶舱"三类，钉钉/企微内嵌端与 H5 未纳入设计。
- 建议：在 PRD 或设计规范中明确钉钉/企微/H5 是"延后"还是"不做"，避免范围理解分歧。

### 【低 / 建议增强】—— 可在三期或后续纳入

**L1.** 驾驶舱"核心指标实时、非核心 T+1"未枚举具体指标清单（7.1）。
**L2.** 非功能性需求缺失：无明确性能 SLA（页面响应、并发用户、全辖报表导出耗时）、无容量与可用性指标。
**L3.** 产品成功指标/KPI 缺失：未量化"基层减负"目标（如减少手工台账 X%、自动生成台账覆盖率）。
**L4.** 数据迁移/初始化策略缺失：从 Excel 或全国党员系统批量导入历史党员/组织数据的方案未定义。
**L5.** 党费结余管理缺失：收缴→上缴→使用后的结余处理与年度结转未说明。
**L6.** 党员证明开具功能缺失（组织关系证明、党员身份证明、党费缴纳证明），该需求高频且可借电子签章闭环。
**L7.** 多来源整改台账（组织生活会/支部考核/党风廉政）是否统一为单一整改跟踪器未明确，存在碎片化风险。

## 五、文档内部一致性问题

1. **发展党员阶段划分不一致**：3.2.2 为 5 阶段，4.1 合并为 4 阶段并将"上级党委备案"移位（详见 H4）。
2. **"25 节点"承诺与正文详略不匹配**：3.2.2 与 4.1 均未真正枚举 25 个节点，仅描述关键动作，与"严格遵循 25 个节点"的断言存在落差。
3. **终端范围收窄**：PRD 五类终端 vs 设计规范三类设计范围（详见 M11）。
4. **移动端功能声明冲突**：PRD 终端层列明的功能 vs 设计规范/落地计划实际移动端清单（详见 M10）。
5. **数据模型覆盖不足**：第六章标题为"核心数据模型设计"，但仅 4 张主数据表，与"全程留痕、不可逆向删除"的设计原则不匹配（详见 H5）。

## 七、总体结论

PRD 在**系统架构、安全合规、数据权限、三会一课与党费主链路**方面设计成熟、闭环严谨，具备良好的落地基础。但作为刚性党务系统，仍存在以下必须正视的问题：

1. **合规层面**：发展党员缺失法定公示环节（H2），且 25 节点未真正落地（H4），存在与《发展党员工作细则》不符的风险。
2. **权限层面**：角色矩阵未覆盖党总支级（H1），四级组织与四级角色错位，权限模型无法精确落地。
3. **数据层面**：核心流程实例、积分、学时、考核、审计等支撑"留痕可溯"的实体未建模（H5），闭环缺乏数据底座。
4. **闭环层面**：组织转接在途状态（H3）、信访举报（H6）、积分自动联动（M1）三处逻辑开口，需在二期前闭合。
5. **范围层面**：移动端与钉钉/企微/H5 终端的范围声明前后不一致（M10/M11），需统一口径。

建议在进入设计细化与开发前，优先以 H1–H7 与 M2 为"准入门槛"完成一轮 PRD 修订，再据此校核设计规范与落地计划，避免带病进入实现阶段。
