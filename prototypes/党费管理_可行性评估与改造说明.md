## 一、背景问题 → 方案映射

| 背景问题 | 原方案 | 可行性评估 | 本次落地 |
|---|---|---|---|
| ① 缺「基础党费缴纳」场景（企业当月不发工资，0.5 元/月）；需每月手动配置核算方法 | 仅工资基数按比例核算 | **可行**。两种核算方式互不冲突，可共用同一台账结构，仅 `method` 字段区分 | 新增「党费缴纳配置」模块，支持 `salary`（工资基数×比例）/ `basic`（固定 0.5 元）两类；`calcShould()` 统一测算 |
| ② 台账数据来源与生成方式未说明（原型原为硬编码静态数据） | 无「配置→生成台账」链路 | **可行且必要**。需建立可解释的数据血缘：配置是数据源，生成动作产出台账 | 梳理数据流 **配置(FEE_CONFIG) → 生成台账(generateLedger) → 明细(FEE_DETAILS) → 汇总(按 org 聚合)**，并在卡片内注明来源 |
| ③ 台账优化（超管视角）汇总展示 + 下钻明细 | 原「缴费台账」仅平铺列表 | **可行**。汇总 = 明细按组织聚合，明细是唯一数据源，避免双写 | 改为「党费汇总台账（超管视角）」：应交/实缴人数、应缴/实缴金额、差额、查看明细下钻 |
| ④ 明细清单增加审核逻辑（上传凭证→审核→已缴） | 无审核环节 | **可行**。引入审核状态机，与缴纳状态分离，避免状态歧义 | 明细表新增 `audit_status`（无需审核/待审核/已通过/已驳回）；`auditPass`/`auditReject` 驱动状态流转 |
| ⑤ 特殊处理：台账补录（新转入/新转正党员缺失） | 无 | **可行**。补录 = 按配置向当月台账追加明细，并联动刷新汇总 | 新增台账补录模态，候选来自「已启用且当月不在台账」的配置人员，提交后同步汇总 |
| ⑥ 数据同步：明细更新后同步汇总 | 手动两张表 | **可行**。所有写操作统一回调 `renderDetail + renderSummary + renderKpis + renderUrge` | 已统一封装，明细任何变更即时回写汇总/KPI/催缴 |

## 二、数据模型设计

```
FEE_CONFIG（人员核算方法 · 台账数据源 · 19 人）
  member_id, name, org, method(salary|basic), salary_base, start_month, created_at, status(enabled|disabled)

FEE_DETAILS（缴费台账明细 · 唯一数据源）
  flow_id, member_id, name, org, ym, method, salary_base, rate,
  should(应缴), actual(实缴), pay_type, pay_time,
  pay_status(未缴|待审核|已缴|补缴|减免|欠缴),
  audit_status(无需审核|待审核|已通过|已驳回),
  voucher_no, operator, notify(已通知|未通知),
  base_start(起缴责任月/历史应缴起始日), consecutiveMiss(连续未缴月数),
  reject_reason, history[]
```

**两种核算方式：**
- `salary`：应缴 = `salary_base × rate`，rate 按中组部 4 档（≤3000→0.5% / ≤5000→1.0% / ≤10000→1.5% / >10000→2.0%），结果与 `Math.round(基数×比例)/100` 一致。
- `basic`：固定 `0.5 元/月`（企业当月不发工资场景），无需工资基数。

## 三、状态机设计

**缴纳状态机 `pay_status`**
```
未缴 ──登记缴费──▶ 已缴
未缴 ──审核通过──▶ 已缴（待审核→已缴）
未缴 ──审核驳回──▶ 欠缴
欠缴 ──补缴──▶ 补缴
未缴/欠缴 ──减免审批──▶ 减免
```

**审核状态机 `audit_status`**
```
无需审核（线下登记/代扣，免审）
待审核 ──auditPass──▶ 已通过（联动 pay_status→已缴）
待审核 ──auditReject──▶ 已驳回（联动 pay_status→欠缴，写入驳回原因）
```

**操作项按状态分显（`detailOps`）**
- 待审核：`通过` / `驳回` / `凭证`
- 未缴·欠缴：`登记缴费` / `减免` / (`欠缴`额外 `补缴`) / `明细`
- 已缴·补缴·减免：`凭证` / `明细` / (`非减免` `减免`)

## 四、数据流（可解释的数据血缘）

```
[党费缴纳配置] FEE_CONFIG  ──(每月手动设置核算方法)──┐
                                                      │ generateLedger()
                                                      ▼
[党费明细台账] FEE_DETAILS  ──(上传凭证/审核/登记/补缴/减免/补录)──┐
                                                      │ renderSummary() 按 org 聚合
                                                      ▼
[党费汇总台账] 超管视角：应交/实缴人数、金额、差额 ──▶ 查看明细下钻二级页面
```

> 配置是**唯一数据源**，台账由配置生成，明细是汇总的**唯一数据源**。任何明细变更经统一回调即时同步汇总，杜绝双写不一致。

## 六、已知简化处理与后续建议

1. **「起缴责任月」与「历史应缴起始日」**：当前明细表两列均取 `base_start`。概念上可区分（后者用于推算历史欠缴区间），原型阶段合并展示，正式开发建议拆分为独立字段 `base_start` / `history_start`。
2. **配置→台账的「启用/停用」语义**：删除配置为逻辑停用（`status=disabled`），历史台账保留；停用人员当月台账生成时自动排除。建议正式环境增加「停用生效月」避免跨月歧义。
3. **审核主体与权限**：原型以固定操作员演示；正式需对接统一身份认证与「超管/支部管理员」角色权限矩阵。
4. **凭证上传**：原型以「上传凭证」按钮 + 凭证号演示；正式需接入文件存储与验真（电子签章）。
5. **金额精度**：党费以「分」为最小单位，已用 `Math.round(x*100)/100` 规避浮点误差，正式建议全程以「分」整数存储。
6. **扩展性**：当前为单文件原型；正式系统应将 `FEE_CONFIG`/`FEE_DETAILS` 映射为 `party_fee_config` / `party_fee_detail` 两张表，并补充台账生成任务调度（月度定时生成草案）。
